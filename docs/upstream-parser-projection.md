## Import the completed parser recipe

The existing webapp wheel is version 0.1.1 based on `3d4d35d3c32ac5b8c14983f99f92c2f633669417`; its `preprocessing.api` is a local packaging patch, not a module present in current upstream. The webapp's extraction entry expects `parse_snapshot(..., source_format=...) -> (document, chunks)`. [Package provenance](../backend/packages/provenance.json), [adapter patch](../backend/packages/content-optimization-library.patch), [webapp extraction](../backend/app/extraction.py).

Current upstream's corpus entry is `trad_ml_scorer.retention_features.parse_snapshot`. It classifies the payload, computes payload-plus-URL snapshot identity, inventories the original source, invokes `extract_conservative` for HTML or `extract_markdown_text` for native sources, and builds `downstream-document-v1`. It returns a document with `chunks`, `scorer_source_word_count`, and immutable raw-source references. Corpus extraction wraps this with offline execution, timeout, location checks, version/run identity and content checksum. Future documents should share these parser modules; they do not need to inherit a corpus run's row/path identity. [Parser](https://github.com/ext-weihsianglin/content-optimization-system/blob/f971b1400d36df2bd3fae7e4e5ed95a3b532da0d/trad_ml_scorer/retention_features.py), [corpus driver](https://github.com/ext-weihsianglin/content-optimization-system/blob/f971b1400d36df2bd3fae7e4e5ed95a3b532da0d/preprocessing/corpus.py).

`conservative_dom` remains the retention-region policy. Markdown conversion is now `markdownify-structured-v1`, using pinned `markdownify==1.2.3` over source-owned blocks (`dom-blocks-v3`). It is not a direct `markdownify(raw_html)` call. Fidelity converters preserve code whitespace and safe fence widths, explicit terminal/break-only content, links/media targets, deletion, literal Markdown syntax, ordered-list starts, and HTML tables/definition containers where plain Markdown is lossy. Source locators remain separate from serialized text. [Serializer and converters](https://github.com/ext-weihsianglin/content-optimization-system/blob/f971b1400d36df2bd3fae7e4e5ed95a3b532da0d/preprocessing/markdownify_serializer.py).

[Feature bundle](/Users/ext-weihsiang.lin/Documents/profound/data/content-optimization-system/representations/runs/markdownify-openai-v1/features/openai-v1.json), [configuration](https://github.com/ext-weihsianglin/content-optimization-system/blob/f971b1400d36df2bd3fae7e4e5ed95a3b532da0d/representations/config.json), [provider](https://github.com/ext-weihsianglin/content-optimization-system/blob/f971b1400d36df2bd3fae7e4e5ed95a3b532da0d/representations/providers.py).

Exact serialization is `blocks-v3-markdownify`. Seven fields are query, document title, each H1, heading outline, page, source-chunk sections, and normalized URL path. V3 blocks use their `inline_markdown` except code, which preserves source whitespace. Tables serialize structured caption/cell/header/span data as deterministic JSON. Sections include ancestor-heading context. Embedding splitting uses UTF-8 byte ceilings: section 4,096 and page/title/outline/path/query 7,000; these are distinct from the parser's 6,000-character chunks. Splits preserve every character, prefer block/whitespace boundaries, and record contributors and ranges. Queries over 7,000 bytes and missing fields remain explicitly unavailable. [Input serializer](https://github.com/ext-weihsianglin/content-optimization-system/blob/f971b1400d36df2bd3fae7e4e5ed95a3b532da0d/representations/inputs.py), [splitter](https://github.com/ext-weihsianglin/content-optimization-system/blob/f971b1400d36df2bd3fae7e4e5ed95a3b532da0d/representations/chunking.py).

When a non-section view spans multiple requests, each member is L2 normalized, weighted by its source-content UTF-8 byte length (excluding heading prefix), summed in float64, then L2 normalized and stored as float32. A pooled unit is unavailable unless every member is available. Individual source-section splits remain individual units. The saved vector lookup also normalizes vectors for alignment/projection. Replacing this with one truncated page request or averaging unnormalized vectors changes the scorer input distribution. [Pooling and vector lookup](https://github.com/ext-weihsianglin/content-optimization-system/blob/f971b1400d36df2bd3fae7e4e5ed95a3b532da0d/representations/runner.py).

The complete run contains 409,730 logical units, 408,746 successful vectors, 354,112 unique requests and zero failed requests; unavailable units remain explicit. The shared cache is `/Users/ext-weihsiang.lin/Documents/profound/data/content-optimization-system/representations/shared-store`. Reuse cached source/query vectors by semantic request identity rather than launching corpus inference again. New future pages or rewritten text require new requests where identity misses. [Run summary](https://github.com/ext-weihsianglin/content-optimization-system/blob/f971b1400d36df2bd3fae7e4e5ed95a3b532da0d/analysis/embedding-markdownify-openai-corpus.json).

Seven separate 32D PCA fits were trained on original eligible training sources, excluding held-out content duplicates and mixed-split query leakage. Inputs are L2 normalized; whitening is false. Large fits use seeded randomized SVD, seed 42, power 3. Future inference must apply saved field-specific `mean` and `components`: `(normalized_vector - mean) @ components.T`; never refit on new pages or GEPA candidates. Original 3,072D cosine is authoritative for semantic alignment; cosine between coordinates from different field PCA bases is invalid. The bundle maps each field to its saved fit and metadata. Whether v7 actually consumes PCA coordinates, original-space alignment or both must be confirmed from the v7 artifact contract; generating PCA coordinates is not itself proof they enter P1. [Projection implementation](https://github.com/ext-weihsianglin/content-optimization-system/blob/f971b1400d36df2bd3fae7e4e5ed95a3b532da0d/representations/projection.py), [feature bundle](/Users/ext-weihsiang.lin/Documents/profound/data/content-optimization-system/representations/runs/markdownify-openai-v1/features/openai-v1.json).

## Integration requirements and verification gates

1. Build a new pinned upstream wheel that includes `preprocessing`, `trad_ml_scorer`, `representations` and required runtime/config assets. Preserve/update the packaging-only `preprocessing.api` contract, including explicit source-format handling, tuple return, candidate diagnostics and the scorer source-word count; do not simply apply the old patch blindly. Record upstream revision, patch and wheel hashes.
2. Read already-completed corpus documents for examples/GEPA; verify saved hashes and join records by original file hash/row and snapshot identity. Future HTML must call the same pinned preprocessing modules. Add bounded offline parity checks against representative saved documents (code, tables, definitions, inline syntax and native formats), comparing blocks, Markdown, chunks, source identity and warning states.
3. Import representation serialization, provider validation, cache identity, normalized pooling and alignment behavior rather than reimplementing them. Freeze model/config/serializer and saved projection references with each P1/GEPA run. Use stub embeddings for normal tests; live embedding calls require an explicit run action.
4. Validate cached-vector and feature parity for frozen source/query records; then compare future-input feature construction against upstream APIs. Do not count a model-name match as parity. Preserve missing/failed embeddings and abstentions rather than silently falling back to lexical-only P1.
5. Audit all webapp block consumers before switching parser versions. Keep original/proposed identities and source-match certificates separate. GEPA rewards must be computed from updated proposal text, not stale `inline_markdown`, original vectors or original source badges.

These gates remain to be executed. This investigation read code and artifact metadata and checked five parser fingerprints; it did not run corpus extraction, inference, model training or full artifact verification.
